### 亮点一：严谨的“第三范式（3NF）”建模与数据完整性体系设计

**（对应报告 1.2 概念/逻辑结构设计 及 1.3 物理结构设计，第 4-8 页）**

#### 1. 亮点具体是什么（做了什么）

该成员没有随意地堆砌字段，而是严格遵循**数据库规范化理论**进行了系统设计：

- 
- **范式验证**：在报告第 5 页，明确阐述了设计思路——将用户基本信息（users）与一卡通业务信息（card）分离，虽然两者是一对一关系，但为了消除非主属性的传递依赖和数据冗余，严格满足了**第三范式（3NF）**的要求。
- **约束前置**：在物理设计阶段（第 6-8 页），将大量业务规则直接转化为数据库层面的强约束。例如：
  - 
  - **CHECK 约束**：强制余额 card_balance >= 0（防止透支），限定状态枚举值（如 recharge_method 只能是“线上/线下”）。
  - **DEFAULT 约束**：为发卡时间、状态等设置合理的默认值。

#### 2. 为什么这是亮点（体现了什么能力）

- 
- **体现了“理论指导实践”的专业性**：很多同学做设计时只是凭感觉分表，导致后期出现数据更新异常或大量冗余。该成员明确提出了“消除传递函数依赖”的设计依据，证明他深刻理解数据库原理中的核心难点——范式理论。
- **构建了数据的“防波堤”**：通过在设计阶段就引入 CHECK 和 NOT NULL 等约束，而不是依赖后端代码去判断（例如金额不能为负），这体现了**“数据驱动”**的设计思想。即使上层代码出现 Bug，数据库底层的约束也能保证脏数据进不来。

#### 3. 为什么老师会认可（符合什么标准）

- 
- **核心考点命中**：数据库课程设计的核心评分点通常就是 **E-R图的正确性** 和 **范式（Normalization）的应用**。能够主动分析并声明自己的设计满足 3NF，是极大的加分项。
- **逻辑闭环**：从第 2 页的“业务需求分析”（如余额不可为负、卡片状态管理）到第 14 页的“约束创建 SQL”，形成了一个完美的逻辑闭环。老师能看到你们是如何把一句文字需求变成一行行严谨的代码的，这正是课程实践的目的。
- **数据严谨性**：这展示了你们对数据完整性的重视，这是数据库设计中最重要的素质之一。

### 亮点二：基于事务（Transaction）机制实现了复杂的业务逻辑闭环

**（对应报告“自定义执行 SQL”部分，第 34 页）**

#### 1. 亮点具体是什么

你们选取了“挂失并补办新卡”这一典型的现实场景，并正确使用了数据库**事务（Transaction）**来保证数据的一致性。

- 
- 代码逻辑清晰：START TRANSACTION -> 锁定旧卡（挂失） -> 插入新卡记录（继承余额） -> 注销旧卡 -> COMMIT。
- 你们没有将这几个步骤割裂为单独的 SQL 执行，而是封装在一个原子操作中。

#### 2. 为什么这是亮点

- 
- **体现了对 ACID 特性的理解**：很多学生只关注 CRUD（增删改查），忽略了数据库核心的“原子性”和“一致性”。你们的设计考虑到了：如果“插入新卡”成功但“注销旧卡”失败怎么办？使用事务机制证明你们思考到了异常处理和数据安全。
- **业务逻辑仿真度高**：你们不仅是存数据，还在管理状态流转（正常 -> 挂失 -> 注销）。逻辑中包含了 INSERT INTO ... SELECT ... 这种高级用法（从旧卡直接复制数据生成新卡），比简单的 INSERT VALUES 更高效且符合工程习惯。

#### 3. 为什么老师会认可

- 
- **符合课程难点要求**：“事务管理”通常是数据库课程的进阶知识点。能够在一个具体的业务场景中正确应用事务，说明你们真正消化了理论知识。
- **数据严谨性**：这展示了你们对数据完整性的重视，这是数据库设计中最重要的素质之一。

### 亮点三：具备明确的 DBA（数据库管理员）运维与安全意识

**（对应报告 3.1 索引重建 与 3.2 用户权限管理，第 24-25 页）**

#### 1. 亮点具体是什么

你们的操作不仅仅局限于“开发者”视角（建表、写 SQL），还包含了“管理员”视角的维护操作：

- 
- **权限最小化控制**：你们创建了专门的 card_user，并只授予了特定表（card_info, consumption_record）的查询权限（GRANT SELECT），而不是直接使用管理员账号（omm）或给所有权限。
- **索引维护意识**：在第 24 页，你们不仅创建了索引，还执行了 REINDEX 命令，并明确注释了原因：“当索引使用时间久、数据频繁增删改导致碎片过多时，需重建索引”。

#### 2. 为什么这是亮点

- 
- **展现了深度的工程思考**：绝大多数学生只知道 CREATE INDEX，很少有人知道索引会产生碎片以及需要维护。这句关于“碎片”的注释非常有含金量，表明你们查阅了资料或对数据库底层存储机制有了解。
- **安全规范**：在很多学生作业中，为了图省事都是 root 权限一把梭。你们展示的“创建用户 -> 授权 -> 验证权限 -> 连接测试”的完整流程，是非常规范的企业级操作流程。

#### 3. 为什么老师会认可

- 
- **符合 openGauss/华为的生态特点**：openGauss 作为一款企业级数据库，非常强调安全（Security）和维护。你们的这些操作非常契合该数据库产品的特性。
- **评分标准中的“规范性”**：数据库安全和性能优化（索引）通常是高分作业的区分点。老师会认为你们不仅会“用”数据库，还懂得如何“管”好数据库。
